## Current Architecture / Workflow Design

### Five-Node Pipeline (as implemented — fully built and wired)

| Node | File | Model | Role |
|------|------|-------|------|
| Orchestrator | `backend/app/orchestrator.py` | None (pure Python) | Routes requests, asyncio.gather(), SSE emission, cache logic |
| Form Workflow | `backend/app/workflows/form_workflow.py` | claude-haiku-4-5 | Extracts TeamFormData → FormEvalJSON (real) or returns dummy |
| Matchup Workflow | `backend/app/workflows/matchup_workflow.py` | claude-haiku-4-5 | Extracts H2H history → MatchupEvalJSON (real) or returns dummy |
| Odds/Risk Workflow | `backend/app/workflows/odds_risk_workflow.py` | claude-haiku-4-5 | Extracts odds + injury data → OddsRiskEvalJSON (real) or dummy |
| Final Prediction Agent | `backend/app/agents/final_prediction.py` | claude-sonnet-4-6 | Synthesizes three eval JSONs → FinalPredictionJSON (real) or dummy |

Note: Model string used in workflow files is `claude-haiku-4-5` (NOT claude-3-5-haiku-20241022 as planned).
Final prediction uses `claude-sonnet-4-6` (correct).

### Schema Package (fully implemented)
Location: `backend/app/schemas/`

- `base.py` — GameContext, SSEEvent, AgentError
- `form.py` — FormEvalJSON (with kebab-case alias_generator), imports H2HGame from matchup.py
- `matchup.py` — H2HGame, MatchupEvalJSON
- `odds_risk.py` — InjuryEntry, OddsRiskEvalJSON
- `prediction.py` — FormWorkflowJSON, MatchupWorkflowJSON, OddsRiskWorkflowJSON, FinalPredictionJSON
- `__init__.py` — re-exports all domain models + legacy models (TeamData, MatchFixture, NBATeamSchema, etc.)

### Tool Pattern (all three workflows + final prediction)
All agents use the same pattern:
1. Build tool schema from Pydantic model_json_schema() at import time
2. Strip fields that are injected programmatically (game_id, team_id)
3. Force tool_choice={"type": "tool", "name": "..."} so model always calls the tool
4. Validate tool_block.input against Pydantic schema before returning

### Data Flow
```
GET /api/analysis/stream/{game_id}?mode=hard|soft
  → FastAPI SSE route (analysis.py)
  → orchestrator.run_pipeline(game_id, mode)
       → _load_context() — reads games.json + form/matchup/odds_risk .txt mock files
       → mode=hard: asyncio.gather(home_form, away_form, matchup, odds_risk) — all 4 concurrent
       → mode=soft: check TTLCache → DB; only run odds_risk fresh; fallback to hard on cache miss
       → final_prediction_agent.run(ctx, home_form, away_form, matchup, odds_risk, partial_telemetry, dummy)
  → SSE events: status | context_loaded | agent_update | agent_error | final_prediction | done
```

### Cache Architecture (two-level)
- **L1 (in-process):** TTLCache (1-hour TTL) in `backend/app/cache/memory.py` — form and matchup only
- **L2 (persistent):** Supabase tables via `backend/app/cache/db.py` — form_cache, matchup_cache, odds_snapshots, recommendations, matches
- **Soft pipeline:** L1 → L2 → hard fallback. Odds/risk is always run live (market-sensitive).

### SSE Event Taxonomy (actual implementation)
- `status` — pipeline status messages (not agent_start as originally planned)
- `context_loaded` — GameContext after _load_context succeeds
- `agent_update` — carries {agent: str, data: dict} when a workflow succeeds
- `agent_error` — carries AgentError payload on partial failure
- `final_prediction` — FinalPredictionJSON payload
- `done` — empty signal, pipeline complete

### API Routes
- `GET /api/matches` — list all fixtures from games.json
- `GET /api/matches/{team_id}` — single fixture (note: uses team_id param but fetches by match id — bug)
- `GET /api/teams` — from teams.py (not read yet)
- `GET /api/analysis/stream/{game_id}` — SSE streaming pipeline
- `GET /api/analysis/{game_id}` — cached analysis (form + matchup, no odds/prediction)
- `GET /api/predictions/{game_id}` — cached FinalPredictionJSON from Supabase
- `POST /command` — UI command handler (GetUpdatedPredictionData → returns stream_url)
- `GET /api/agent_analysis/stream` — legacy polling SSE from agent_analysis.json

### Mock Data
Location: `backend/app/mock_data/`

- `form/LAL.txt`, `form/GSW.txt` — raw form text for Haiku extraction
- `matchups/LAL_GSW.txt` — raw H2H text for Haiku extraction
- `odds_and_risk/LAL_GSW.txt` — raw odds + injury text for Haiku extraction

### Dummy Data
Location: `backend/app/workflows/dummy_data.py`
- `_DUMMY_FORMS: dict[str, FormEvalJSON]` — keyed by team_id (LAL, GSW)
- `_DUMMY_MATCHUPS: list[MatchupEvalJSON]` — matched by game_id substring

## Bugs & Issues Identified (2026-05-23 audit)

### Bug 1 — `form_workflow.py`: Schema not $ref-resolved
`_BASE_SCHEMA = copy.deepcopy(FormEvalJSON.model_json_schema())` — FormEvalJSON contains a nested H2HGame field (`recent_game`). The schema will contain a `$ref` to H2HGame in `$defs`. Unlike `final_prediction.py` which has a `_resolve_refs()` function, the form workflow does NOT resolve refs before sending to the Anthropic tool API. This will cause a tool schema error at runtime with real LLM calls.
**Fix:** Apply the same `_resolve_refs()` pattern from final_prediction.py.

### Bug 2 — `games.py`: `game_id` undefined in error path
In `get_match()`, the 404 error handler references `game_id` but the parameter is named `team_id`. This will raise a `NameError` at runtime.
```python
# Line 53 — references undefined `game_id`
raise HTTPException(..., detail=f"No fixture found for game_id '{game_id}'.")
```
**Fix:** Change `game_id` to `team_id` in the error message, or rename the parameter.

### Bug 3 — `supabase.py`: Typo in env var name
`os.getenv("SUPABASE_API_SECRECT_KEY")` — "SECRECT" is a typo (should be "SECRET"). If the .env file uses the correct spelling `SUPABASE_API_SECRET_KEY`, this silently returns None and the client raises RuntimeError on startup.
**Fix:** Correct the typo, ensure .env matches.

### Bug 4 — `FormEvalJSON`: kebab alias_generator may break DB round-trip
`alias_generator=_to_kebab` converts field names to kebab-case (e.g., `game_id` → `game-id`). When `form.model_dump()` is stored in Supabase `payload` column and later loaded via `FormEvalJSON.model_validate(res.data[0]["payload"])`, the round-trip requires the stored JSON to use kebab-case keys OR `populate_by_name=True` must handle it. The current `model_dump()` without `by_alias=True` stores snake_case, which should round-trip fine. But sending the schema to the Anthropic API via `model_json_schema()` will show kebab-case property names — which is what the LLM will use when calling the tool. The manual injection `tool_input["game_id"] = ctx.game_id` uses snake_case, but the tool input from the LLM will use kebab-case keys like `"game-id"`. This is a schema/injection mismatch.
**Fix:** Either remove the alias_generator or ensure the strip-and-inject logic uses the aliased field names.

### Bug 5 — `matchup_workflow.py`: `_DUMMY_MATCHUPS` lookup bug
`next((matchup for matchup in _DUMMY_MATCHUPS if ctx.game_id in matchup.game_id), None)` — this checks if `ctx.game_id` is a substring of `matchup.game_id`. For game_id="LAL_GSW", and dummy game_id="LAL_GSW", this works. But for a game_id like "LAL_GSW_22_5_26" it would check if "LAL_GSW_22_5_26" is IN "LAL_GSW" — which is False. The check should be reversed: `matchup.game_id in ctx.game_id` or use startswith.
Same bug exists in `odds_risk_workflow.py`.
**Fix:** Reverse the `in` check or use startswith.

### Bug 6 — `final_prediction.py`: No try/except around API call
The `anthropic_client.messages.create()` call is not wrapped in try/except. The orchestrator catches exceptions via `return_exceptions=True` for the parallel workers, but the final_prediction call is wrapped in its own try/except in the orchestrator — so it's safe there. However per operational protocol, all Anthropic SDK calls should have local error handling with structured logging.
**Fix:** Wrap in try/except for anthropic.APIConnectionError, anthropic.RateLimitError.

### Gap 1 — `form_workflow.py` and `matchup_workflow.py`: No try/except on API calls
Same as Bug 6 — no local exception handling around messages.create().

### Gap 2 — `cache/memory.py`: TTLCache not thread-safe
`time.monotonic()` + dict operations are not atomic. Under high concurrency this could cause race conditions. Low priority for current scale.

### Gap 3 — `analysis.py`: Legacy `/api/agent_analysis/stream` polling loop
This is a holdover from before the pipeline was built. It polls a static `agent_analysis.json` file in an infinite loop. The file may not exist. This route should either be removed or clearly marked as deprecated.

### Gap 4 — No docstrings on any workflow functions
The `run()` function in each workflow has no Google-style docstring. Per operational protocol, all public functions must have docstrings.

### `backend/app/api/games.py` — Bug 2 confirmed on line 53
- `game_id` is referenced but the parameter is `team_id`. NameError at runtime.
- Also: the log on line 46 uses an f-string without the `f` prefix: `"Recieved GET request for {team_id}"` — typo in spelling ("Recieved") and missing `f`.

### `backend/app/main.py` — Inline comment artifact
- Line 22: `# <-- Change this from the hardcoded string list to your variable!` — stale comment, CORS is already using the `origins` variable correctly.

### `backend/app/cache/supabase.py` — Bug 3 confirmed on line 17
- `SUPABASE_API_SECRECT_KEY` typo confirmed. Env var name in error message also uses the typo, so the error message itself will be misleading.

### Dummy data lookup logic — Bug 5 confirmed
- `matchup_workflow.py` line 38: `ctx.game_id in matchup.game_id` — checks if the full ctx.game_id string is a substring of the dummy's shorter game_id. For ctx.game_id="LAL_GSW_22_5_26" and dummy.game_id="LAL_GSW", this is False. Falls back to `_DUMMY_MATCHUPS[0]` which works, but only because there's a fallback. The logic is still wrong conceptually.
- Same pattern in `odds_risk_workflow.py` line 35.

### `FormEvalJSON` Bug 4 confirmed — kebab alias + field injection mismatch
- `_BASE_SCHEMA` in `form_workflow.py` will have property keys like `"team-name"`, `"last-10-wins"`, etc. (kebab-case) because alias_generator converts underscores to dashes.
- After `tool_block.input`, the LLM returns a dict with kebab-case keys (e.g., `"last-10-wins": 4`).
- `tool_input["game_id"] = ctx.game_id` injects using snake_case.
- `FormEvalJSON.model_validate(tool_input)` with `populate_by_name=True` would accept snake_case `game_id` but would also need to handle the kebab keys from the LLM. Since `populate_by_name=True` is set, validation should accept both alias and field name — but the LLM will use aliases (kebab), so the dict has mixed key styles (LLM uses kebab, our injection uses snake). This is potentially fragile but may work due to `populate_by_name=True`.

### Bug 1 confirmed — `form_workflow.py` missing `_resolve_refs()`
- `FormEvalJSON` schema will contain `$defs` with `H2HGame` and a `$ref` in the `recent_game` property.
- The Anthropic tool API does not support `$ref` pointers in tool schemas — it requires flat, inlined schemas.
- `form_workflow.py` does NOT call `_resolve_refs()`. This WILL break real LLM calls.
- `matchup_workflow.py` has the same issue: `MatchupEvalJSON.h2h_last_10` and `last_h2h` both reference `H2HGame` via `$ref`.
- `odds_risk_workflow.py` may also have an issue: `OddsRiskEvalJSON.injury_report` is a `list[InjuryEntry]` — the schema may generate a `$defs` entry for `InjuryEntry`.
